- Both untrusted claim `observation_interval.lower/upper` and signed `verified_observation_interval.lower/upper` are **JSON strings containing canonical base-10 signed int64 Unix nanoseconds**, matching `^(0|-?[1-9][0-9]*)$`. Canonical byte hash = SHA-256 of JCS UTF-8 `signed_subject` with those unaltered canonical strings.

## C. Exact branch-specific source binding (DP-R3-FND004-C)

The independently trusted source must separately attest to the **same exact bytes**, including binding purpose, source key epoch, and resource scope. A string matching another claimant string is not authentication.

For `NO_EXTERNAL_FIRST_EFFECT_ATTEMPT`, require `verified_binding_source.kind=NO_EXTERNAL_PREDICATE_INSTANCE` and a canonical document with **exactly** the keys `binding_kind=NO_EXTERNAL_PREDICATE_INSTANCE_BINDING_V1`, `request_id`, `predicate_instance_id`, `no_external_attempt_reason`, `interface`, `effect_id`, `resource_id`, `principal_id`, `artifact_chain_id`, `root_sha256`, `challenge_nonce`, `nonce_replay_namespace`. `verified_binding_source.canonical_binding_document_sha256` MUST equal `request_attempt_binding_sha256`; its `authenticated_source_witness_sha256` MUST match independently fetched/authenticated attestation bytes binding the same source document and purpose. ## G. DP-R3.2 — Lossless epoch and sequence identity (FND-DPR31-NEW-001)

1. **Normative status:** candidate verification rule only; **neither adopted nor implemented**. The 19 previously unbounded nonnegative JSON integers in `04A` (8 common/legacy-claim rows and 11 signed subject/source/policy rows) become **canonical unsigned ASCII decimal JSON strings** in this distinct `CANDIDATE_DP_R3_2` protocol. Required lexical form is `^(0|[1-9][0-9]*)$`, `minLength=1`, `maxLength=128` ASCII digits, with `0` the only zero spelling. Negative, `+`, exponent, fractional, whitespace, leading-zero, Unicode numeral, boolean, null, and **raw JSON number token** are forbidden. This size bound is a candidate resource-exhaustion cap, not an invented provider capability or unsigned-int hardware guarantee. Exact arithmetic is arbitrary-precision; no IEEE-754 serialization or Number/float anywhere in the trust decision.
2. **Input handling BEFORE JCS:** independently obtain the exact raw JSON bytes; reject invalid UTF-8, duplicate object keys, invalid numeric tokens in protected fields and any lossy transcoding by a parser before canonicalization. Build a typed lossless data model; validate lexical strings, parse to exact arbitrary-precision nonnegative integers without rounding, enforce maximum length, and only then canonicalize the signed JSON subject using RFC 8785. If the original bytes have been lossy-parsed without access to the raw tokens, **reject** as `UNKNOWN/NOT_PROVEN/NO_CURRENT`, never infer a faithful original.
3. **Independent source-to-subject-to-claim join:** all issuer, DB term/sequence, signer/verifier/source key epoch, denial/provider/internal policy epoch, and verification-check epoch are exact canonical strings in `04A`: outer claim (`properties.issuer_epoch/db_term/db_sequence/policy_epoch/proof_issuer_key_epoch`), legacy claimant `verified_evidence`/`verification_receipt` untrusted fields, `verified_subject`, `denial_before_effect_proof`, both `verified_binding_source` variants and both policy variants. Verify exact canonical string equality **and independently authenticated numeric source value** for each matched field. Do not equate a shared string with independent evidence; authenticated source bytes and actor/attempt/effect/root/policy/epoch/digest bindings remain mandatory. Branch-specific `NOT_APPLICABLE` does not create a provider epoch. A missing relevant field, mismatched source or ambiguity is `UNKNOWN/CONFLICT/NO_CURRENT`.
4. **Distinctness oracle:** `"9007199254740992"` and `"9007199254740993"` are distinct valid *candidate lexical strings* (and distinct exact integers). Replacing either in a signed key epoch, DB sequence, or policy epoch MUST change the JCS UTF-8 signed_subject bytes and computed digest; an independently verified signature/witness cannot cover the swapped value. `9007199254740992` (without quotes) and `9007199254740993` (without quotes) are both rejected in these typed fields; do not allow float-based rounding to map them to the same identity. Case `04E` records this as **paper-only NOT_EXECUTED**.
5. **Version/profile binding:** schema `protocol_version.const=CANDIDATE_DP_R3_2`, signed subject version `...DP-R3_2...`, independent receipt version `...DP-R3_2...`, canonicalization profile `RFC8785_JCS_I_JSON_UTF8_WITH_DECIMAL_NS_AND_UNSIGNED_EPOCH_STRINGS_R3_2`. The signer/verifier profile remains externally pinned and **NONE_ADOPTED**. R3.1 epochs represented as JSON numbers must **never be silently translated**, even if safely small, since migration requires fresh formal Owner normative adoption and trust reassessment. JSON Schema validates string structure only; it cannot authenticate provider rights, signatures, clock calibration or complete mediation.
